# Hands-on Redis Curriculum (Expanded)

Oct 9, 2026 · @krishnamn · expanded by @d1ttb

A 4-week, lab-first path from zero to running Redis as an in-memory data store, cache, queue, stream processor and leaderboard. Plan on about 1 hour a day, plus one weekend for the capstone.

> **Version note:** These labs target **Redis 8.x**. Redis 8 includes JSON, the Query Engine (search), time series and probabilistic types in the core server, and adds the AGPLv3 license option. Everything here also works on **Valkey**, the open-source fork, except the module-based features in the appendix.

---

## How to use this curriculum

1. **Learn in this order:** redis-cli first, then Python. Typing commands by hand builds the mental model; the client library just wraps those commands.
2. **Finish each lab before moving on.** Every module has a lab with a checklist. A lab counts as done when the checklist is complete and you've written down what you saw in `NOTES.md`.
3. **Expect to break things.** Redis runs in Docker, so `docker rm -f redis` resets everything.
4. **Keep `MONITOR` open in a spare terminal** from Module 4 onward. It shows exactly which commands your code sends.

## Module 0: Setup (30 min)

**Goals:** have a disposable Redis instance, a CLI and a GUI ready.

```bash
docker run -d --name redis -p 6379:6379 redis:8
docker exec -it redis redis-cli
# Optional: GUI
docker run -d --name redisinsight -p 5540:5540 redis/redisinsight:latest
```

- [ ] Run `PING` and get `PONG`
- [ ] Run `SET hello world`, then `GET hello`
- [ ] Run `INFO server` and note `redis_version`
- [ ] Run `INFO memory` and note `used_memory_human`
- [ ] Open RedisInsight at http://localhost:5540 and connect to `host.docker.internal:6379` (Mac/Windows) or the container IP (Linux)
- [ ] Learn `MONITOR` (it streams every command; you'll use it to watch your Python code later)
- [ ] Learn `redis-cli --stat`, `redis-cli --bigkeys` and `redis-cli --latency`

**Mental model:** Redis executes commands on a single main thread and keeps typed data structures in RAM. Each command is atomic. Speed comes from memory, simple O(1)/O(log n) operations and no query planner, so the real skill is choosing the right structure for each problem. Redis 6+ uses extra threads only for network I/O.

## Module 1: Strings, keys and TTL (1.5 h)

Strings hold text, integers, floats or raw bytes up to 512 MB. Counters, flags, locks and cached blobs are all built on them.

```bash
SET user:1:name "Ada"
GET user:1:name
INCR page:home:views
INCRBY page:home:views 10
INCRBYFLOAT price:sku1 0.5
SET token:abc 1 EX 60 NX     # set only if absent, expire in 60s
TTL token:abc                # -1 = no TTL, -2 = key missing
PTTL token:abc               # milliseconds
EXPIRE user:1:name 300
PERSIST user:1:name          # remove TTL
GETEX user:1:name EX 60      # get + reset TTL
GETDEL token:abc
MSET a 1 b 2 c 3
MGET a b c
EXISTS a
TYPE a
OBJECT ENCODING a            # int / embstr / raw
DEL a
UNLINK big:key               # non-blocking delete
SCAN 0 MATCH user:* COUNT 100 TYPE string
```

**Key concepts**

- Namespace keys with colons, like `object:id:field`, and keep the convention consistent across services.
- Use `SCAN` on real data, never `KEYS *`. `KEYS` is O(N) and blocks the server.
- `SET ... NX EX` is the building block for locks and idempotency keys.
- `INCR` is atomic, so concurrent clients never lose counts.
- Expiry works two ways: lazily, when a key is accessed, and actively, through sampling about 10 times per second. Expired keys can stay in memory briefly.
- Use `UNLINK` instead of `DEL` for large keys, so memory is freed in a background thread.

**Lab: page-view counter**

- [ ] Add a per-day key like `views:2026-10-07:<slug>` that expires after 7 days (`SET ... EX 604800` on first write, or `INCR` + `EXPIRE ... NX`)

## Module 2: Hashes, lists and sets (2 h)

```bash
# Hashes: objects with fields
HSET user:1 name Ada email ada@x.io plan pro
HGET user:1 name
HMGET user:1 name plan
HGETALL user:1
HINCRBY user:1 logins 1
HEXPIRE user:1 60 FIELDS 1 plan     # per-field TTL (Redis 7.4+)
HTTL user:1 FIELDS 1 plan

# Lists: queues and stacks
LPUSH jobs "resize:42"
RPUSH jobs "email:7"
RPOP jobs
BRPOP jobs 5                        # blocking pop, waits up to 5s
LMOVE jobs jobs:processing RIGHT LEFT    # reliable-queue handoff
BLMOVE jobs jobs:processing RIGHT LEFT 5
LRANGE jobs 0 -1
LTRIM recent 0 99                   # keep a capped list

# Sets: unique members, set algebra
SADD tags:post:1 redis cache nosql
SADD tags:post:2 redis streams
SINTER tags:post:1 tags:post:2
SINTERCARD 2 tags:post:1 tags:post:2
SUNION tags:post:1 tags:post:2
SDIFF tags:post:1 tags:post:2
SISMEMBER tags:post:1 cache
SMISMEMBER tags:post:1 cache redis go
SCARD tags:post:1
SRANDMEMBER tags:post:1 2
```

**When to use which**

| Need | Structure | Why |
| --- | --- | --- |
| Object with fields | Hash | Update one field without rewriting the whole value |
| FIFO job queue | List | `LPUSH` + `BRPOP` is O(1) and blocking |
| Queue that survives worker crashes | List + `LMOVE` | The job stays in a processing list until it's acknowledged |
| Capped recent items | List + `LTRIM` | Bounded memory |
| Unique items, membership | Set | O(1) add and lookup |
| Common/different members | Set | `SINTER`, `SUNION`, `SDIFF` |

**Why small hashes are cheap:** Small hashes, lists and sets use compact encodings (`listpack`, `intset`) until they grow past thresholds such as `hash-max-listpack-entries`. That's why 1,000 small hashes can use far less memory than 1,000 JSON strings.

## Module 3: Sorted sets (2 h)

Sorted sets keep unique members ordered by a numeric score, which makes them the most versatile Redis structure. Internally they're a skip list plus a hash table, so most operations are O(log n).

```bash
ZADD board 1500 alice 1200 bob 1800 carol
ZADD board GT 1400 alice            # only update if the new score is greater
ZINCRBY board 50 bob
ZRANGE board 0 2 REV WITHSCORES     # top 3 (modern syntax)
ZREVRANK board alice                # 0-based rank from top
ZSCORE board carol
ZRANGE board 1000 1600 BYSCORE
ZRANGE board 0 -1 BYLEX             # lexicographic when scores are equal
ZRANGESTORE top10 board 0 9 REV
ZPOPMAX board                       # also BZPOPMIN for priority queues
ZREM board bob
ZCARD board
ZCOUNT board 1000 2000
```

**Sliding-window rate limiter pattern**

```bash
# allow max 5 requests per 60s per user
ZREMRANGEBYSCORE rl:u1 0 <now_ms - 60000>
ZCARD rl:u1                 # if >= 5, reject
ZADD rl:u1 <now_ms> <unique_id>
EXPIRE rl:u1 60
```

**Rate limiting alternatives**

| Algorithm | Redis primitive | Trade-off |
| --- | --- | --- |
| Fixed window | `INCR` + `EXPIRE` | Cheapest, but allows bursts at window edges |
| Sliding log | Sorted set (above) | Exact, but O(requests) memory |
| Sliding window counter | 2 `INCR` keys, weighted | Approximate, cheap |
| Token bucket / GCRA | Hash + Lua | Smooth, burst-friendly (see [brandur/redis-cell](https://github.com/brandur/redis-cell)) |

## Module 4: Caching patterns and eviction (2 h)

Caching is the most common production use of Redis.

| Pattern | How it works | Risk |
| --- | --- | --- |
| **Cache-aside** (lazy) | App reads the cache; on a miss, reads the DB and writes the cache with a TTL | Stale data until TTL or invalidation |
| **Write-through** | App writes the DB and the cache together | Write latency, caches unread data |
| **Write-behind** | App writes the cache; a worker flushes to the DB | Data loss if Redis dies |
| **Refresh-ahead** | Refresh hot keys before their TTL ends | Complexity |

```bash
CONFIG SET maxmemory 50mb
CONFIG SET maxmemory-policy allkeys-lru
CONFIG GET maxmemory*
INFO stats          # keyspace_hits, keyspace_misses, evicted_keys, expired_keys
INFO keyspace
OBJECT FREQ mykey   # needs an LFU policy
OBJECT IDLETIME mykey
MEMORY USAGE mykey
MEMORY DOCTOR
```

**Eviction policies to know**

| Policy | Evicts | Use when |
| --- | --- | --- |
| noeviction | Nothing; writes fail when full | Redis is a primary store |
| allkeys-lru | Least recently used, any key | General-purpose cache (best default) |
| allkeys-lfu | Least frequently used, any key | Hot/cold skew |
| volatile-lru / volatile-lfu | Same, but only keys with a TTL | Mixed cache and persistent keys |
| volatile-ttl | Soonest-expiring keys with a TTL | Mixed, TTL as priority |
| allkeys-random | Random | Uniform access |

Redis's LRU and LFU are approximations: it samples `maxmemory-samples` keys (default 5) and evicts the best candidate. Raising the sample count improves accuracy at some CPU cost.

**Cache stampede defenses**
1. **TTL jitter:** `ex = base + random(0, base*0.2)` stops many keys from expiring at once.
2. **Single-flight lock:** on a miss, `SET lock:<key> 1 NX PX 5000`. The winner recomputes while the others wait briefly or serve stale data.
3. **Probabilistic early expiration (XFetch):** recompute early with a probability that rises as the TTL nears zero.
4. **Client-side caching** (Redis 6+ `CLIENT TRACKING`): the server pushes invalidations to clients that cache locally.

## Module 5: Streams, pub/sub and probabilistic types (2.5 h)

Streams are an append-only log with consumer groups, so messages persist and can be replayed. Pub/sub is fire-and-forget: if nobody is listening, the message is lost.

```bash
# Streams
XADD events MAXLEN ~ 10000 * type click user 42   # capped stream
XLEN events
XRANGE events - +
XREVRANGE events + - COUNT 5
XGROUP CREATE events workers $ MKSTREAM
XREADGROUP GROUP workers w1 COUNT 10 BLOCK 5000 STREAMS events >
XACK events workers <message-id>
XPENDING events workers
XPENDING events workers - + 10 w1
XAUTOCLAIM events workers w2 60000 0-0 COUNT 10    # take over idle msgs
XINFO GROUPS events
XINFO CONSUMERS events workers
XTRIM events MINID <id>

# Pub/sub
SUBSCRIBE news            # terminal A
PSUBSCRIBE news.*         # pattern subscribe
PUBLISH news "hello"      # terminal B
PUBSUB CHANNELS
SSUBSCRIBE / SPUBLISH     # sharded pub/sub in Cluster (Redis 7+)

# Compact counting
PFADD uniq:visitors u1 u2 u3
PFCOUNT uniq:visitors     # approximate distinct count, ~0.81% error, 12 KB max
PFMERGE uniq:week uniq:mon uniq:tue
SETBIT active:2026-10-07 42 1
BITCOUNT active:2026-10-07
BITOP AND active:both active:2026-10-07 active:2026-10-08

# Redis 8 built-in probabilistic types
BF.ADD seen:urls https://a.io      # Bloom filter
BF.EXISTS seen:urls https://a.io
CMS.INITBYDIM cms 2000 5           # Count-Min Sketch
TOPK.RESERVE topk 10
```

**Streams vs lists vs pub/sub vs Kafka**

| | Pub/sub | List queue | Stream | Kafka |
| --- | --- | --- | --- | --- |
| Persistence | No | Yes | Yes | Yes (disk) |
| Multiple consumer groups | Fan-out only | No | Yes | Yes |
| Replay | No | No | Yes (by ID) | Yes |
| Acknowledgements | No | Manual | `XACK` + PEL | Offsets |
| Size limit | n/a | RAM | RAM (trim it) | Disk |

## Module 6: Persistence, transactions, pipelining and Lua (3 h)

Memory is volatile, so you decide how much data you can afford to lose.

| Mode | How | Loss on crash | Restart speed |
| --- | --- | --- | --- |
| None | No persistence | Everything | Instant (empty) |
| RDB | Forked snapshot every N sec/changes | Minutes | Fast |
| AOF `everysec` | Log of every write, fsync each second | ~1 s | Slower (replay) |
| AOF `always` | fsync on every write | ~0 | Slowest writes |
| RDB + AOF | Both; Redis 7 uses multi-part AOF with an RDB base | ~1 s | Good |

```bash
CONFIG SET appendonly yes
CONFIG SET appendfsync everysec
CONFIG SET save "3600 1 300 100 60 10000"
BGSAVE
BGREWRITEAOF
LASTSAVE
INFO persistence

# Transactions: queued, executed together, no interleaving
MULTI
DECRBY stock:sku1 1
RPUSH orders sku1
EXEC
# Note: there's no rollback. If one command errors at runtime, the others still run.

# Optimistic locking
WATCH balance:1
GET balance:1
MULTI
DECRBY balance:1 20
EXEC               # returns (nil) if balance:1 changed after WATCH

# Lua: atomic read-modify-write
EVAL "local s = tonumber(redis.call('GET', KEYS[1])); if s and s > 0 then return redis.call('DECR', KEYS[1]) else return -1 end" 1 stock:sku1

# Cache scripts by SHA
SCRIPT LOAD "<script>"
EVALSHA <sha> 1 stock:sku1

# Redis Functions (7+): named, persisted, replicated libraries
FUNCTION LOAD "#!lua name=shop\nredis.register_function('decr_stock', function(keys) ... end)"
FCALL decr_stock 1 stock:sku1
```

**Atomic sliding-window rate limiter** (`scripts/rate_limit.lua`)

```lua
-- KEYS[1] = rl:<id>; ARGV = now_ms, window_ms, limit, member
local key, now, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count >= limit then
  return {0, count}
end
redis.call('ZADD', key, now, ARGV[4])
redis.call('PEXPIRE', key, window)
return {1, count + 1}
```

**Safe lock release** (follow-up to Module 1)

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

**MULTI vs WATCH vs Lua**

| Need | Use |
| --- | --- |
| Batch writes, no reads in between | `MULTI/EXEC` |
| Read, then conditional write, with low contention | `WATCH` + `MULTI` (retry on nil) |
| Read, then conditional write, with high contention or complex logic | Lua / Functions |
| Fewer round trips, atomicity not needed | Pipeline |

## Module 7: Python app with redis-py (3 h)

```bash
pip install "redis[hiredis]" fastapi uvicorn pytest testcontainers
```

```python name=labs/m07_api/cache.py
import json, random, time, uuid
import redis

pool = redis.ConnectionPool(host="localhost", port=6379, decode_responses=True,
                            max_connections=50, health_check_interval=30)
r = redis.Redis(connection_pool=pool)

def slow_db_lookup(uid: int) -> dict:
    time.sleep(0.5)
    return {"id": uid, "name": f"user{uid}"}

def get_user(uid: int) -> dict:
    key = f"user:{uid}"
    if (hit := r.get(key)):
        return json.loads(hit)
    # single-flight: only one caller recomputes
    if r.set(f"lock:{key}", 1, nx=True, px=5000):
        try:
            user = slow_db_lookup(uid)
            r.set(key, json.dumps(user), ex=300 + random.randint(0, 60))
            return user
        finally:
            r.delete(f"lock:{key}")
    time.sleep(0.05)
    return get_user(uid)

# Pipeline: one round trip for many commands
with r.pipeline(transaction=False) as p:
    for i in range(1000):
        p.set(f"k:{i}", i)
    p.execute()

# Registered Lua script (uses EVALSHA, falls back to EVAL automatically)
rate_limit = r.register_script(open("scripts/rate_limit.lua").read())

def allow(ip: str, limit=5, window_ms=60_000) -> bool:
    now = int(time.time() * 1000)
    ok, _ = rate_limit(keys=[f"rl:{ip}"], args=[now, window_ms, limit, f"{now}-{uuid.uuid4()}"])
    return bool(ok)
```

```python name=labs/m07_api/main.py

@app.middleware("http")
async def limiter(request: Request, call_next):
    if not allow(request.client.host):
        from fastapi.responses import JSONResponse
        return JSONResponse({"detail": "Too Many Requests"}, status_code=429)
    return await call_next(request)

@app.get("/users/{uid}")

@app.post("/leaderboard/{player}/{points}")

@app.get("/leaderboard")

    return r.zrange("board", 0, n - 1, desc=True, withscores=True)
```

## Module 8: Replication, Sentinel and Cluster (3 h)

Replication copies one primary to read-only replicas, asynchronously by default. Sentinel watches them and promotes a replica when the primary dies. Cluster shards keys across many primaries using 16,384 hash slots (`CRC16(key) mod 16384`).

| Setup | Solves | Pick it when |
| --- | --- | --- |
| Single node | Nothing; simplest | Dev, or a small cache you can afford to lose |
| Primary + replicas | Read scaling, a hot copy | Reads dominate |
| Sentinel (3 nodes) | Automatic failover | Data fits on one machine, but you need uptime |
| Cluster | Failover plus more RAM than one machine | The dataset or write load outgrows one node |

```yaml name=docker/sentinel/compose.yml
services:
  redis-primary:
    image: redis:8
    command: redis-server --appendonly yes
  redis-replica-1:
    image: redis:8
    command: redis-server --replicaof redis-primary 6379
  redis-replica-2:
    image: redis:8
    command: redis-server --replicaof redis-primary 6379
  sentinel-1: &sentinel
    image: redis:8
    command: redis-sentinel /etc/sentinel.conf
    volumes: ["./sentinel1.conf:/etc/sentinel.conf"]
  sentinel-2:
    <<: *sentinel
    volumes: ["./sentinel2.conf:/etc/sentinel.conf"]
  sentinel-3:
    <<: *sentinel
    volumes: ["./sentinel3.conf:/etc/sentinel.conf"]
```

```conf name=docker/sentinel/sentinel1.conf
sentinel resolve-hostnames yes
sentinel monitor mymaster redis-primary 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 10000
sentinel parallel-syncs mymaster 1
```

Sentinel rewrites its config file at runtime, so give each Sentinel its own writable copy.

```bash
# Replica pointing at a primary
REPLICAOF redis-primary 6379
INFO replication
WAIT 1 1000                     # block until 1 replica acks (not true sync durability)

# Sentinel
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
redis-cli -p 26379 SENTINEL replicas mymaster

# Cluster (6 nodes: 3 primaries, 3 replicas)
redis-cli --cluster create host1:7000 host2:7001 host3:7002 host4:7003 host5:7004 host6:7005 --cluster-replicas 1
redis-cli -c -p 7000           # -c follows MOVED redirects
CLUSTER INFO
CLUSTER NODES
CLUSTER SHARDS
CLUSTER KEYSLOT user:1
redis-cli --cluster reshard host1:7000
```

**Failure semantics to understand**
- Replication is asynchronous. Acknowledged writes on the old primary can be lost during failover.
- A split brain is possible. `min-replicas-to-write` / `min-replicas-max-lag` limit the damage.
- Cluster multi-key commands, transactions and Lua scripts need all keys in one slot. Use hash tags like `{user:1}:cart`.

## Capstone and self-assessment

Pick one capstone, build it over about a weekend, and write a one-page README that explains each key's **type, TTL, eviction behavior and why you chose it**.

| Capstone | Redis features exercised | Reference implementations to study |
| --- | --- | --- |
| URL shortener with click analytics | Strings, INCR, HyperLogLog, TTL, sorted set of top links | Search GitHub `topic:url-shortener redis` |
| Real-time game leaderboard API | Sorted sets, pub/sub or streams for live updates, hashes for profiles | [redis-developer](https://github.com/redis-developer) org samples |
| Background job system with retries | Lists or streams, consumer groups, sorted set for delayed jobs, Lua | [rq/rq](https://github.com/rq/rq), [taskforcesh/bullmq](https://github.com/taskforcesh/bullmq) |
| Session + rate-limit gateway | Hashes, HEXPIRE, Lua sliding window, Sentinel failover | [brandur/redis-cell](https://github.com/brandur/redis-cell) |
| Semantic search / RAG cache (Redis 8) | Vector sets or the Query Engine, JSON, TTL | [redis/redis-vl-python](https://github.com/redis/redis-vl-python) |

**Capstone grading rubric**

| Criterion | Pass |
| --- | --- |
| Data model | Every key documented with its type, TTL and reasoning |
| Correctness | No race conditions; atomic paths use Lua or MULTI |
| Resilience | Survives `docker kill` with documented loss; reconnects after failover |
| Performance | p99 reported under load, with and without Redis |
| Tests | Integration tests run against a containerized Redis in CI |

**You're done when you can do all of this without notes:**

- [ ] Choose the right data structure for a new problem and justify it in one sentence
- [ ] Explain RDB vs AOF and pick a durability setting for a stated loss tolerance
- [ ] Pick an eviction policy and prove it works with `INFO stats`
- [ ] Make a multi-step operation atomic with MULTI or Lua and say when each is needed
- [ ] Diagnose a slow Redis using `SLOWLOG GET`, `INFO`, `MONITOR`, `LATENCY DOCTOR` and `MEMORY USAGE`
- [ ] Explain what happens to your app when the primary fails, including which writes might be lost
- [ ] Explain why Cluster needs hash tags for multi-key operations
- [ ] Lock down an instance with ACLs and TLS

**Common mistakes to avoid:** using `KEYS *` in production, storing huge values or unbounded lists, forgetting TTLs on cache keys, treating pub/sub as durable, `DEL` on huge keys, running without `maxmemory`, exposing port 6379 to the internet without auth, assuming `MULTI` rolls back, and assuming replication is synchronous.
